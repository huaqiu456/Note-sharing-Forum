# 异常错误码

## 一、统一响应结构

所有服务返回同一个包装结构（`com.huaqiu.framework.common.response.Response`）：

```json
{
  "success": true,
  "message": null,
  "errorCode": null,
  "data": {}
}
```

| 字段 | 说明 |
| --- | --- |
| `success` | 是否成功，默认 `true` |
| `message` | 提示信息（失败时给前端展示） |
| `errorCode` | 业务错误码 |
| `data` | 业务数据 |

构造方式：

| 方法 | 用途 |
| --- | --- |
| `Response.success()` / `success(data)` | 成功 |
| `Response.fail(String errorMessage)` | 仅错误信息（无错误码） |
| `Response.fail(errorCode, errorMessage)` | 错误码 + 信息 |
| `Response.fail(BizException)` / `fail(BaseExceptionInterface)` | 从枚举/异常构造 |

## 二、错误码规范

格式：`{模块前缀}-{五位数字}`

```
AUTH-10000        模块    编号
 └─┬─┘ └──┬──┘
  模块     编号
```

**编号分段约定**（从现有代码归纳）：

| 段位 | 含义 | 示例 |
| --- | --- | --- |
| `x10000` | 通用/系统异常 | `AUTH-10000`、`NOTE-10000` |
| `x10001` | 参数校验失败 | `AUTH-10001`、`NOTE-10001` |
| `x20000` 起 | 业务异常 | `NOTE-20000` 未知笔记类型 |
| `x30000` 起 | 认证/账号类异常 | `AUTH-30000` 未注册 |

> 网关是例外：它直接用 HTTP 状态码字符串 `"401"`、`"403"`、`"500"` 作为 `errorCode`。

## 三、各服务错误码清单

### 1. 网关 xiaohashu-gateway

| errorCode | 含义 | HTTP 状态 | 触发场景 |
| --- | --- | --- | --- |
| `401` | 未登录或登录已过期 | 401 | Sa-Token 校验登录失败 |
| `403` | 权限不足，无法发布 | 403 | 已登录但缺少 `app:note:publish` |
| `500` | 系统繁忙，请稍后再试 | 200（业务失败） | 其它未捕获异常 |

### 2. 认证服务 xiaohashu-auth

| errorCode | 含义 |
| --- | --- |
| `AUTH-10000` | 出错啦，后台小哥正在努力修复中...（系统异常兜底） |
| `AUTH-10001` | 参数错误（`@Validated` 校验失败） |
| `AUTH-20000` | 请求太频繁，请3分钟后再试（验证码重复发送） |
| `AUTH-20001` | 验证码错误 |
| `AUTH-30000` | 用户还没注册，请用手机验证码注册 |
| `AUTH-30001` | 用户密码错误 |

### 3. 笔记服务 xiaohashu-note

| errorCode | 含义 |
| --- | --- |
| `NOTE-10000` | 出错啦，后台小哥正在努力修复中...（系统异常兜底） |
| `NOTE-10001` | 参数错误 |
| `NOTE-20000` | 未知的笔记类型 |
| `NOTE-20001` | 笔记发布失败 |
| `NOTE-20004` | 笔记更新失败 |

> 编号不连续（缺少 `NOTE-20002`、`NOTE-20003`），为历史遗留。

### 4. 用户服务 xiaohashu-user

| errorCode | 含义 |
| --- | --- |
| `USER-20001` | 昵称请设置2-24个字符，不能使用@《/等特殊字符 |
| `USER-20002` | 小哈书号请设置6-15个字符，仅可使用英文、数字、下划线 |
| `USER-20003` | 性别错误 |
| `USER-20004` | 个人简介请设置1-100个字符 |

> 该服务**没有通用异常码**（无 `USER-10000` / `USER-10001`），也没有全局异常处理器，见第五节问题说明。

### 5. 对象存储 xiaohashu-oss

**未定义错误码枚举**。上传失败会抛出运行时异常，走 Spring 默认错误响应。

### 6. KV 服务 xiaohashu-kv（已废弃）

代码位于 `xiaohashu-kv-duplicate/` 目录，**未加入根 pom modules、不参与构建**。其错误码仅供历史参考：

| errorCode | 含义 |
| --- | --- |
| `KV-10000` | 系统异常 |
| `KV-10001` | 参数错误 |
| `KV-20000` | 笔记内容不存在 |

## 四、异常处理机制

### 核心类

| 类 | 作用 |
| --- | --- |
| `BaseExceptionInterface` | 错误码接口（`getErrorCode` / `getErrorMessage`） |
| `BizException` | 业务异常，由错误码枚举构造 |
| `ResponseCodeEnum` | 各服务自有的错误码枚举 |
| `GlobalExceptionHandler` | 全局异常处理器，把异常转成 `Response` |

### 处理链路

```
业务代码
  └─ throw new BizException(ResponseCodeEnum.XXX)
        ↓
  GlobalExceptionHandler
        ├─ BizException            → Response.fail(e)                （保留错误码与信息）
        ├─ MethodArgumentNotValid  → Response.fail(PARAM_NOT_VALID)  （拼接字段校验信息）
        ├─ IllegalArgumentException→ Response.fail(PARAM_NOT_VALID)  （note 服务）
        └─ Exception（兜底）        → Response.fail(SYSTEM_ERROR)      （不暴露内部细节）
```

### 日志级别约定

| 异常类型 | 日志级别 |
| --- | --- |
| 业务异常 `BizException` | `warn`（预期内的失败） |
| 参数校验失败 | `warn` |
| 未知异常 | `error`（带完整堆栈） |

### 各服务处理器覆盖情况

| 服务 | 处理器 | 类型 |
| --- | --- | --- |
| gateway | `GlobalExceptionHandler` | `ErrorWebExceptionHandler`（WebFlux） |
| auth | `GlobalExceptionHandler` | `@ControllerAdvice` |
| note | `GlobalExceptionHandler` | `@ControllerAdvice` |
| user | **无** | — |
| oss | **无** | — |

## 五、HTTP 状态码与业务错误码

项目里两类错误并存，含义不同：

| 类型 | 表现形式 | 前端处理 |
| --- | --- | --- |
| HTTP 状态码 | 401 / 403 / 502 等 | 按状态码分支处理 |
| 业务错误码 | 响应体 `errorCode` 字段 | 弹 `message` 提示 |

### 前端处理约定（`web/src/utils/request.ts`）

| 情况 | 前端行为 |
| --- | --- |
| HTTP 401 | 清除 token，跳转登录页 |
| HTTP 403 | 仅提示「权限不足」，**不清 token、不跳登录** |
| 其它 HTTP 错误 | 提示响应体 `message` 或网络错误 |
| `success = false` | 提示 `message`，并 reject |

> 401 与 403 必须区分：早期实现把「无权限」也返回 401，导致普通用户点发布被踢到登录页。

## 六、现存问题与改进建议

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| **user 服务没有全局异常处理器** | `BizException` / 参数校验异常会走 Spring 默认响应，**不返回统一 `Response` 结构**，前端拿不到 `message` | 参照 note 服务补 `@ControllerAdvice` |
| **oss 服务无错误码、无处理器** | 上传失败返回默认错误体，前端提示不友好 | 定义 `OSS-xxxx` 错误码与处理器 |
| 网关错误码直接用数字字符串 | 与其它模块 `XXX-10000` 风格不一致 | 可统一为 `GATEWAY-10000` 等 |
| user 用 `IllegalArgumentException` 传错误文案 | 丢失错误码，只保留 message | 改用 `BizException(ResponseCodeEnum.XXX)` |
| note 错误码编号不连续 | `NOTE-20002/20003` 缺失，阅读困惑 | 补齐或重排（注意兼容） |
| KV 错误码仍在仓库 | 容易被误认为在用 | 删除 `xiaohashu-kv-duplicate` 目录 |

## 七、快速排查

| 前端看到 | 定位方向 |
| --- | --- |
| `AUTH-10000` | auth 服务内部异常，看 auth 日志 `request error` 堆栈 |
| `AUTH-20001` | 验证码错误（Redis 中的验证码与提交值不一致） |
| `NOTE-10000` | note 服务内部异常，看 note 日志 |
| `USER-xxxx` 但无 message | user 服务缺全局异常处理器，看服务日志 |
| HTTP 401 | token 缺失/失效 |
| HTTP 403 | 已登录但缺权限（检查 Redis 中角色与权限数据） |
| HTTP 502 | 网关或上游不可达（见《业务流转/07-权限校验.md》与部署排障） |
